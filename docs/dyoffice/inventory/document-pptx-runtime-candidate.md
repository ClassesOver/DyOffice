# PPTX module content candidate, not an approved runtime

## Actual deliverable

The offline builder bundles the real
apps/web/worker/src/native/pptx-session.ts entry with existing esbuild 0.25.12,
Node/CJS output, Node24 target, explicit ES2022/useDefineForClassFields config,
markdown text loader, minification and retained EOF legal comments. It does
not import or execute the generated module. No ZIP code, document parser,
production route, runtime resolver or T06 commit path is changed.

The fixed candidate is pptx-edit-v1 / policy 1, x86_64, intended future target
distributions openEuler and Ubuntu. productionEnabled, runtimeApproved and
rootfsComplete are all false. This is a JS module, not a bootable filesystem.

Node's mature crypto.createHash('sha256') hashes actual compiler input snapshots
and the generated bytes. A domain-separated digest binds the canonical manifest:
fixed recipe, profile, policy, target, source identifiers/modes/sizes/hashes,
package names/versions/package.json hashes, external builtins, output path/mode/
size/hash, and esbuild wrapper/native compiler hashes and Node/tool versions.
ESBUILD_BINARY_PATH overrides are rejected. The existing Linux x86_64 compiler
package is read and hashed, not downloaded or independently launched by the
builder. esbuild itself uses its normal build service.

onLoad supplies the same bytes that it records to esbuild. Paths use stable
workspace-relative or package-name@version-relative identifiers, not local
absolute paths. All loaded sources are bounded individually (16 MiB), together
(64 MiB) and by count (1024); output is capped at 16 MiB. JSON manifest reads are
capped at 1 MiB. Builtin imports only are permitted in the generated module;
other external packages fail the build. Legal comments are retained, not stripped
to hide build paths. No source maps are emitted.

## Local source evidence

For this run, an independent artifact-build tree was materialized with the exact
workspace blobs from commit e0d5be4201ed4f90595a3664b05eb4e5101d9257.
The actual build loaded 97 workspace sources, each byte-for-byte checked against
that remote tree, and 111 dependency inputs from the existing read-only package
cache. Six workspace package manifests and apps/web/package.json were also
checked before materialization. Dependency symlinks were explicit test setup;
they were not treated as authenticated workspace source. The loaded dependencies
have actual byte hashes and package versions, not a supply-chain certification.
The source-check JSON, build tree, cache links and generated artifact are local
test evidence and are not committed.

This is new current-source checking, not reuse of the older 96-source attestation.
Git blob identity/source commit evidence is separate from manifest SHA-256 content
identity. The builder itself does not contact GitHub or certify a commit.

## Verification and threat boundary

preparePptxCandidate returns a new temporary directory and its contentDigest.
verifyPptxCandidate requires that expected digest **from outside the directory**.
Reading a directory's own manifest is not trusted identity. The verifier requires
canonical JSON bytes (no extra whitespace, duplicate keys or trailing content),
the exact file list, expected mode, regular single-link files, bounded reads and
matching artifact SHA-256. Leaf symlinks are rejected using O_NOFOLLOW;
nonblocking opens avoid waiting on a substituted FIFO. Extra/missing files,
symlinks, hardlinks, altered modes and a self-consistent replaced file/manifest
are rejected when the original expected digest remains pinned.

This validates read snapshots only. Ordinary directories are mutable, and
parent-directory replacement/hash-then-exec TOCTOU is NOT solved. No result may
be upgraded to a production grant or execution-by-path permission. Source roots
and output parent are trusted offline operator configuration, not document
request input. Tools execute as trusted build tooling; hashes identify observed
tool bytes but do not certify the compiler process or all of its dependencies.
onLoad is not a complete resolver-input/lockfile/OS build provenance capture.
The explicit tsconfig avoids auto-discovered compiler settings, but package
resolution and the surrounding dependency installation still require independent
supply-chain review.

Node executable, shared libraries, OS package closure, fonts, licenses and actual
host sandbox probes remain unprovided. The module's dependent Node builtins are
listed, not bundled into an executable rootfs. Repeat builds from the same local
inputs produce the same content digest; this is not reproducible compiler-build
proof, cross-platform reproducibility or a license/distribution approval.

## Test recipe

In a complete exact checkout with its existing dependencies:

    node --test apps/web/test/runtime-artifacts/pptx-candidate.test.mjs

In this partial workspace, set DYOFFICE_ARTIFACT_SOURCE_ROOT to the independently
materialized exact source tree. The test builds twice and validates real output
bytes, canonical identity, mutation rejection, extra/missing files, wrong modes,
link rejection, profile change and independent-digest mismatch. A removed
expected-digest comparison was tested as a mutation and caused the self-consistent
replacement case to fail; the comparison was restored. No generated code is
executed, no PG/runtime services are started, and no host security setting changes.

The verifier also enforces the fixed recipe, pinned esbuild version, target
distribution list, unverified provenance flags, exact field shapes, sorted unique
bounded input records and builtin list. Even a newly supplied matching digest
does not turn an arbitrary manifest into this fixed candidate type. The expected
digest remains the independent identity anchor, not an authorization credential.

Listed external imports do not prove absence of dynamic require or filesystem
resource access at runtime. This minified output was tested for build identity
and tampering only. The earlier non-minified PPTX save tests do not constitute
functional validation of these exact generated bytes.

## Offline CLI

    node apps/web/scripts/prepare-pptx-runtime-candidate.mjs prepare EXISTING_OUTPUT_PARENT
    node apps/web/scripts/prepare-pptx-runtime-candidate.mjs verify CANDIDATE_DIRECTORY EXPECTED_DIGEST

Prepare fixes its source root to the script's repository and accepts no custom
entry, command, environment or compiler flags. Verify requires an independently
held digest. Success JSON always states nonlaunchable, runtimeApproved=false,
rootfsComplete=false and productionEnabled=false; it is not a runtime install.
The integration test invokes the actual verify CLI and rejects extra arguments.

The CLI prepare regression also uses an isolated non-hoisted source tree:
esbuild's optional native package is available from esbuild's own installation,
not from the script root. Resolving it from the script initially failed; the
builder now resolves with createRequire(require.resolve('esbuild')), matching
the wrapper's package lookup rather than using PATH. Both actual prepare and
verify CLI operations pass, and the isolated build matches the original digest.
The fixed esbuild version is checked before invoking build, not only afterward.

Before extracting the ordinary 0777 permission bits, every file read rejects
any SUID, SGID or sticky mode bit (07000). This is a read-only metadata check,
not a permission change. The guard is explicit in bytesOf and is checked by source inspection;
tests retain real ordinary-mode 0600 rejection without creating special-mode
files or changing host security settings.
