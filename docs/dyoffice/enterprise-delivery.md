# DyOffice 企业落地与持续运营计划

> 版本 1.0 · 2026-11-15。本文中的容量、时限、成本与服务指标是建议的规划/验收目标，不是当前系统能力、已签 SLA 或已执行结果。
> 配套：[总体架构](architecture.md) · [实施任务](implementation-plan.md) · [验收矩阵](acceptance-matrix.md)。

## 1. 企业交付的定义

企业落地不是把开发服务放到服务器上，也不是把套餐名字改成“企业版”。完成条件是：客户的真实文件和用户能持续、安全地使用；出了故障能定位、止损、恢复；升级不破坏已有文件；有清楚的能力边界、费用、责任人与交付证据。

保留既定产品范围：多用户各自拥有个人工作区，不建设团队、组织成员、团队授权、共享编辑和 CRDT 协作。企业管理员做全局配置与运维；账号在 DyOffice 管理后台本地创建、停用和维护，不依赖外部身份服务；管理员不因此获得团队权限或个人文档读取权。首批优先一客户一部署，模型、对象存储、数据库、密钥和管理员配置均在该部署边界内。

### 1.1 首批可验证业务场景

| 场景 | 完整操作链 | 企业收益如何测量 |
| --- | --- | --- |
| 制度/方案文档 | 上传 DOCX -> AI 阅读/改写 -> 修订审阅 -> 保存 -> 下载 -> Word 复开 | 人工起草和复核时间、返工次数、格式损坏率 |
| 经营数据分析 | 只读数据源/上传 XLSX -> 核对单位与期间 -> 公式/图表 -> 可追溯解释 -> 归档 | 对账耗时、引用可定位率、公式/数值错误数 |
| 汇报材料 | 选择授权附件/数据 -> 生成原生 PPTX -> 人工编辑 -> 下载/展示 | 初稿时间、可编辑对象比例、人工修正时间 |
| PDF 审阅与处理 | 打开 PDF -> 问答定位 -> 批注/支持的文本编辑 -> 导出 -> 重开 | 检索定位时间、处理成功率、隐私数据泄漏事件 |
| 外部 Agent 控制 | 用户授权 Token -> HTTP MCP -> 已打开编辑器 -> 确认修改 -> 保存回执 | 可执行率、误操作率、重连重复写入次数 |

不以“模型回答看起来不错”评价价值。每个试点场景都记录旧流程基准、使用 DyOffice 的总耗时、复核耗时、失败和费用；节约时间需扣除人工检查成本。

## 2. 页面与交互交付范围

### 2.1 登录和工作区

登录采用 DyOffice 本地用户名和密码，由服务端创建会话并通过安全 Cookie 维护；提供忘记密码（首版向管理员申请重置）、修改密码、退出登录和自己的会话管理。过期后暂停敏感操作，重新登录后先检查文件版本，不能悄悄覆盖。工作区包括文件夹、最近、收藏、回收站、搜索、格式过滤和上传/新建。列表显示文件格式、更新时间、版本/同步状态，操作包括打开、重命名、移动、下载、删除和恢复。

上传展示实际进度、校验状态、格式/体积限制；失败可重试且不产生幽灵文件。相同名称允许按明确规则生成新文件，不凭名称覆盖。搜索结果中的预览、缩略图和文件名本身也遵守所有权边界。

### 2.2 编辑器和 AI

复用原编辑器工具栏、页面/工作表/幻灯片导航和 AI 面板，不重新设计低功能替代编辑器。统一顶部状态为“已保存/正在保存/未保存/离线草稿/版本冲突/只读”，显示服务端已提交版本。AI 区提供选择模型（仅 Admin 已启用）、附件、引用、停止、变更摘要、预览、确认和撤销。

明确区分“AI 已生成”“已应用到文档”“已保存到服务器”。流式生成期间用户仍能理解哪些内容可编辑；选区冻结失效后拒绝旧操作。原生文档功能不可用时说明具体原因，不让用户尝试后才丢数据。历史版本预览不改变当前版本；恢复生成新版本。

桌面浏览器优先完整编辑，移动端先保证登录、阅读、下载和适合的轻量操作；完整移动编辑不能未经实测宣称等价。浏览器/版本支持表随 release manifest 固定。保持键盘导航、焦点管理、可读错误、中文输入法、无障碍标签和上游 i18n；主题不得影响文件颜色。

### 2.3 个人设置、数据源和集成

个人设置保留主题、语言、作者、自动保存、助手位置/显示及个人技能选择。个人数据源支持新增、编辑、测试、删除、预览已授权 schema 和只读结果；密码只显示“已配置”，测试失败不清空草稿。

“外部连接”页面显示当前用户的 MCP 地址、作用域、批准的文件范围、Token 前缀、到期时间和撤销入口；明文 Token 仅创建时显示。用户不能配置服务器 stdio 命令，不能改全局服务 URL 或读取其他用户 Token。URL Token 测试入口在生产构建/运行配置中明确关闭。

### 2.4 Admin、任务和审计

Admin 按模型、图像生成、图像/视频分析、网页/图片搜索、重排、HTTP MCP、数据源连接器、默认策略和密钥状态分组。配置保存有 revision 冲突提示；连接测试使用当前已保存或明确标记的草稿配置，不能混淆。禁用能力须反映到所有编辑器，不能只隐藏菜单。

任务页展示所属用户、类型、状态、进度、错误编号、取消和安全重试资格；普通用户只见自己。运维默认看指标/元数据而非全文。审计员可按权限导出脱敏事件；运维或配置管理员没有隐式文档读取特权。

## 3. 上线前客户调研与交付输入

销售或技术负责人填写交付问卷，答案成为项目参数而非无期限待办：

| 项目 | 必须取得的输入 | 无输入时的保守默认 |
| --- | --- | --- |
| 业务 | 3–5 个优先场景、成功指标、业务验收人 | 仅脱敏样本，不处理真实敏感数据 |
| 用户与身份 | 管理员名单、用户名分配规则、首次管理员初始化、密码策略、批量开户、离职停用与重置审批规则 | 仅受控测试账号，公开自助注册默认关闭，生产无默认管理员密码 |
| 数据 | 文档分类、外发规则、地域、保留/删除要求 | 外部模型/搜索/MCP 默认关闭 |
| 文件 | 每格式代表样本、字体、密码/签名文件、最大体积 | 采用验收矩阵标准包，特殊样本列为限制 |
| 数据源 | 端点/端口、认证、数据库类型、只读角色和表范围 | 不开放任意连接串和公网抓取 |
| 网络 | 域名/TLS、代理、WS/SSE、私网、出站 allowlist | 同源 HTTPS，未经批准的出站禁止 |
| 运维 | 部署区、监控、备份目标、值班、RPO/RTO | 不承诺 HA 或自动恢复 |
| 采购与成本 | 模型供应商、客户自带 Key/平台 Key、存储和费用限额 | 小额度试点，按观测结果扩容 |

法规适用、数据处理协议、供应商条款、保留期限和字体/组件许可由客户合规与法务共同审查；不得把本技术方案当作已通过某项认证或法律合规结论。

## 4. 部署形态与基础设施

### 4.1 开发与演示

使用独立开发配置、测试数据、可替换本地对象存储，开发 Token 只在本地/隔离环境。开发机器能启动不代表 release image 可启动。Electron 桌面依赖、系统字体和原生二进制必须在构建清单中明确，不依靠开发机隐含环境。

### 4.2 企业试点：独立部署

推荐 Docker Compose/客户容器平台承载 API、Worker、PostgreSQL、Redis 与 S3 兼容对象存储；也可连接客户已有托管服务。允许先单节点，但在风险单明确单点故障、维护窗口和恢复方式。客户间不共享数据库管理员凭据、存储桶访问密钥或加密主密钥。

供压测起步的资源假设：API 2–4 vCPU/4–8 GiB、Worker 4–8 vCPU/8–16 GiB、数据库 2–4 vCPU/8 GiB、Redis 1–2 GiB，存储单独估算。它们是实验起点，不是“可承载多少用户”的保证；必须用目标样本测量 CPU、内存、IO、连接数和模型并发后调整。

### 4.3 企业生产：经过验证的高可用

只有客户需要并完成演练后才提供 HA 配置：多 API 副本、独立 Worker 池、具备故障切换的 PostgreSQL、持久/高可用队列、可靠对象存储、负载均衡和可恢复密钥管理。WS 连接归属某 API 实例，命令状态与文件租约不依赖该实例内存；掉线重连后通过权威状态恢复。跨实例通知可使用 Redis，但通知丢失时能重新查询，不丢业务状态。

不强制 Kubernetes；客户已有 Kubernetes 时交付 Helm/NetworkPolicy/PDB 等适配及操作文档。无集群经验的客户可用容器+托管数据服务，但必须如实说明故障域。数据库、副本、备份不能全部落在同一块易失磁盘上。

### 4.4 网络与网关要求

只暴露 HTTPS 产品入口（含本地登录、管理页面与受授权 API）；数据库、Redis、对象管理端、Worker 控制端不公开。浏览器同源访问，Admin 可叠加 VPN/IP 限制。代理正确转发 WS Upgrade、禁用 SSE 缓冲并配置心跳与空闲超时；上传大小、请求超时与应用限制一致，不能代理 60 秒超时导致后台写入仍在进行但前端误判失败。

严格校验 Origin；经过认证后仍验证每个资源。敏感下载优先走鉴权代理，需要预签名 URL 时设置极短有效期并告知撤销不能追回已经签发或下载的数据。监控、日志和 trace 不把查询串、Token、完整文档或用户提示词发往第三方。

## 5. 企业安全控制清单

### 5.1 身份与权限

企业账号由 DyOffice 本地管理：管理员创建用户名、发放一次性激活凭据、停用/恢复用户及批准重置密码；用户可凭旧密码自行更改。密码采用 Argon2id 单向散列（带独立 Salt），默认至少 15 字符的长密码策略；登录按 IP/账户限流、失败反馈统一，禁止密码枚举。会话采用安全 HttpOnly Cookie + CSRF/Origin 校验；配置 Admin 采用单独授权与敏感操作再认证。普通用户、配置管理员、运维和审计员职责分离；停用或修改密码后撤销会话、API Token、编辑租约和任务写权限，长期任务在敏感步骤重验。详细约束见 [本地账号认证设计](local-account-auth.md)。

首版不自动转移离职用户的个人文件给管理员。根据客户留存政策，由授权、留痕的迁移/紧急访问流程处理。紧急访问记录理由、批准人、有效期和访问范围，不能是永久“全能管理员”。


### 5.1.1 本地账号运营与恢复

部署时交互式创建首个管理员，不提供固定默认账户或密码；审批首批账号清单，普通用户不能自助升权。管理员可查看账户状态、角色、最近登录失败摘要、执行停用和一次性密码重置，但看不到旧密码，也不因账号管理权获得个人文件所有权。首次激活和密码重置令牌一次性、短效、服务端只保存哈希，日志不记录明文。

管理员丢失密码时，按双人复核的运维恢复预案使用受控 CLI 或短期恢复凭据，记录原因和恢复结果；不得用数据库直接覆盖明文密码。生产发布前必须演练登录被爆破、账号停用、重置与改密后旧会话失效，以及管理员账号丢失后的安全恢复。账号批量导入只允许经批准的 CSV/管理操作，不能把开发环境单一令牌自动映射为所有正式用户。

### 5.2 数据分类与 AI 外发

建议分类为公开、内部、受限；客户可映射到自己的制度。受限数据默认不出批准的部署边界，只有明确允许的 Provider/搜索/MCP/重排端点可接收。外发策略作用于文本、附件、图片、音视频、索引片段和日志，而不只作用于聊天输入框。

默认最小上下文：只传与任务相关的段落、范围和引用，不把所有工作区文件打包发给模型。隐藏区域、个人脱敏规则和企业策略统一评估；未经授权不能用 headless/CLI/MCP 绕过。客户自带模型 Key 仍不等于允许任意敏感数据外发。

离线/内网部署需要本地可用模型、依赖镜像、字体和 SDK 制品；网页搜索、外部 MCP 等不可用时明确关闭。没有本地模型不能把“离线编辑可用”宣传成“离线 AI 全功能可用”。

### 5.3 文件和原生处理

上传结构验证、恶意内容扫描、ZIP 展开预算、外部关系限制、渲染进程沙箱都必须存在。初始建议硬上传上限 50 MiB；压缩格式还需独立设置展开总量、条目数、单条目和 CPU/内存限制，以压力样本校准，不仅看压缩前大小。

Worker 非 root，临时目录按 job 隔离，根文件系统只读，不挂 Docker socket 或主机任意目录；只允许已批准命令与参数，默认禁网。转换或字体失败返回可操作的错误，不能保存空白或缺字版本后宣称成功。

PDF 数字签名、密码、真实脱敏与普通覆盖批注必须区别提示。尚未经过“不可恢复原文”验证的操作不标为安全脱敏。

### 5.4 软件供应链

固定依赖与容器摘要，生成 SBOM，扫描直接/传递依赖和原生二进制，保留 GenOffice 许可证和 NOTICE。字体、图标、媒体模型生成内容、第三方搜索/重排和数据库驱动逐项审查授权与分发方式。向客户交付字体合法安装/替代说明，不随意再分发未知授权字体。

使用受保护分支、代码审查、最小 GitHub Actions 权限、构建秘密隔离及镜像签名。新客户端或 MCP SDK 大版本升级需要兼容回归，不因 latest 发布自动进入生产。

## 6. 数据迁移与上线切换

### 6.1 原型数据迁移

原型 `state.json` 是单用户存储，迁移前由管理员明确指定目标用户。只读导出、文件清单、sha256、总字节、原加密密钥和配置先备份；dry-run 发现未知归属、损坏文件、重复 ID 或缺失密钥时阻止写入。

迁移顺序：身份映射 -> workspace -> 不可变对象 -> 文件版本元数据 -> 偏好 -> 数据源和配置密文重加密 -> 引用/索引 -> 校验。迁移脚本幂等；记录原 ID 到新 ID 的映射；不覆盖原数据。索引可重建，文件和密钥不可凭空重建。

### 6.2 客户文件导入

保留原文件，先小样本再批量；按支持能力分类为可编辑、只读、受保护、损坏、暂不支持。客户确认导入报告后再切换日常工作。大量文件导入限制并发，索引任务不能占满交互 Worker。

### 6.3 灰度切换

生产切换前冻结 release manifest、数据库 schema、配置版本、模型目录和回滚镜像。先导入少量授权用户，观察保存、错误率、成本和工单；达到门槛再扩围。回滚不只回容器，还检查 schema 是否向后兼容、队列协议和已写文件格式。破坏性迁移必须另设维护窗口与恢复点。

## 7. 备份、恢复与连续性

### 7.1 目标与数据范围

建议企业标准目标：RPO 不超过 15 分钟、RTO 不超过 4 小时；严格客户可提出更小值，但必须另做容量与恢复实测。试点单机不能自动承诺该目标。RPO 以一次一致性恢复中可用的文件/元数据为准，不只看数据库 WAL 延迟。

必须备份 PostgreSQL 数据及恢复链、S3 文件版本/对象清单、加密 keyId 对应密钥或恢复授权、身份/全局配置、部署制品和审计。Redis 不是文件真相；可根据 PostgreSQL 重建安全任务，但不可重放已提交或结果不明的外部写入。

PostgreSQL 时间点恢复需要基础备份与连续 WAL；它本身不恢复对象存储、外部密钥和数据库配置文件，必须纳入整体恢复清单。[E1]

### 7.2 建议保留策略

试点默认建议：文件历史至少 30 天、回收站 30 天、备份 35 天、安全审计 180 天；这些值不是法规要求，按客户合同/分类策略在交付参数中确认。配额达到上限时先通知和阻止新增，不静默删除当前文件。法律保留或调查冻结与常规清理冲突时以已批准的保留策略为准，并留痕。

永久删除涵盖当前元数据、历史对象、索引、缓存和生成附件；备份中的残留按既定到期策略处理并向客户说明，不能声称点击删除即抹除所有离线备份。

### 7.3 恢复演练

每次生产首发前，在隔离环境从实际备份恢复；此后建议每季度及重大存储/加密变更后演练。按数据库恢复点核对所有 revision 引用对象的存在和哈希；保留对象版本通常比 DB 保留窗口更长，避免 DB 可回到某点但对应文件已清掉。

恢复后抽检四格式打开/编辑/下载、用户隔离、Admin 密文解密、旧引用定位、任务不重复、审计完整；记录实际耗时和数据损失窗口。密钥找不到、对象缺失或 RTO 超标均算失败，不能靠备份作业显示绿色放行。

## 8. 监控、服务目标与故障响应

### 8.1 可观测性

仪表盘至少包括：API 成功率和 p95/p99；文件保存成功/冲突/失败；已保存却缺少对象的完整性扫描；模型连接/首 token/完成时间及取消率；Provider 错误与成本；WS 在线/重连/命令未知结果；任务队列深度和死信；原生进程 CPU/内存/OOM；数据库连接/慢查询；存储空间；审计和备份新鲜度。

基础设施/程序故障与模型内容质量分开；供应商耗时不混入本地 API 延迟，但端到端用户耗时仍应展示。日志关联 traceId/runId/commandId，不记录完整输入和秘密。告警必须演练到达真实接收人，不能只展示在 Grafana 上。

### 8.2 初始服务目标

建议普通业务 API 月度可用性目标 99.9%，按生产请求口径和排除项双方定义后再签 SLA。AI 供应商不可用时仍能编辑和保存，明确报告依赖故障。容量基线和性能验收详见 acceptance-matrix；没有测量前不向客户承诺“千人并发”。

生产超过错误预算或出现文件完整性异常时冻结功能发布，优先稳定性修复。费用异常可以停止新 AI run，不影响下载和保存已有文件。

### 8.3 事故处置

| 等级 | 典型事件 | 立即动作 | 恢复条件 |
| --- | --- | --- | --- |
| Sev0 | 跨用户泄漏、密钥泄漏、大面积文件损坏 | 停止相关入口/写入，撤销令牌，保存脱敏证据并通知负责人 | 安全/数据负责人确认根因、影响、修复和恢复结果 |
| Sev1 | 核心保存/登录/打开不可用 | 降级非核心 AI/转换，回退兼容版本或切换依赖 | 核心链路验证、无继续损坏风险 |
| Sev2 | 单一 Provider、格式特性或个别用户故障 | 显式降级、保留原件、提供有边界的替代流程 | 定向回归与客户复核 |

建议试点和保障期明确值班覆盖、Sev0/1 通知渠道与响应目标；没有值班人员不能写成 7x24 保证。事故后输出时间线、影响用户/文件、补救措施、回归测试和预防任务。

## 9. 验收与交付节奏

### 阶段 A：交付就绪

项目方交付冻结版本、支持矩阵、架构/威胁模型、部署包、配置样例、SBOM/许可清单、账号管理手册、首次管理员安全初始化、备份恢复手册、运维仪表盘、已知限制及测试证据。客户提供环境/数据/首批用户与管理员清单/模型服务和验收人。环境或凭据不足标 blocked，不写“验收通过”。

### 阶段 B：试点

建议 5–20 名代表用户，覆盖四格式及实际业务，至少 10 个工作日。每个场景至少有一次完整业务任务和一次失败恢复演练；记录使用次数、成功、失败、人工修正、时间及费用。试点发现的问题按 P0/P1/P2 分级；业务关键路径中不能用“以后再优化”接受数据损坏或越权。

### 阶段 C：生产放行

业务负责人确认能完成目标场景；技术负责人确认文件与集成正确性；安全负责人确认外发/隔离/高危关闭；运维负责人确认监控/恢复/回滚；产品负责人确认支持边界与 UI 文案一致。所有必要签收完成后再扩围。详见 acceptance-matrix 的 release gate。

### 阶段 D：移交与保障

培训普通用户（保存/冲突/引用/AI 审批）、Admin（模型/密钥/能力）、运维（告警/备份/恢复/升级）、支持人员（日志编号/复现/分类）。建议明确 2–4 周强化保障期；此后按约定服务级别运营。每月回顾成本、成功率、安全修复、需求和依赖升级。

## 10. 角色、责任和沟通

| 责任 | 项目方 | 客户方 |
| --- | --- | --- |
| 产品范围/支持矩阵 | 产品/技术负责人维护 | 业务负责人确认场景与排除项 |
| 代码、测试、升级 | 开发 + QA | 提供代表样本与 UAT |
| 数据和外发授权 | 实现策略与审计 | 数据/安全负责人批准 |
| 基础设施/备份 | 交付可运行方案、演练脚本 | 指定 SRE/运维和恢复资源 |
| 身份和离职停用 | 本地账号、密码、会话、重置、锁定及撤销实现 | 指定账号管理员、审批创建/停用/重置与紧急恢复 |
| 模型与数据库 | 连接器、错误隔离和预算 | 提供合法有效服务、权限与限额 |
| 验收与商业 | 输出证据和已知风险 | 签收、付款节点与服务责任确认 |

代码审查与关键安全验收不由同一个 AI 输出自动自证。AI 可生成实现/测试/文档，人类负责人对业务正确性、环境准入、数据外发和生产放行负责。

## 11. 成本、商业包装与价值验证

推荐先以“独立部署的软件使用权 + 实施交付 + 可选年度维护”界定采购范围；AI 费用可使用客户自带 Key 或明确计量转付。此为商业建议，不预设具体售价。合同中区分产品功能、客户定制、基础设施、模型费用、上线验收、支持时段和升级。

月度总成本模型：基础设施 + 存储/备份 + 网络 + 模型文本/媒体/重排 + 第三方服务 + 运维/支持。模型成本按供应商实际报告和计费单位结算；缺失用量先标 unknown 并核对，不能计为零。预算按用户/部署/能力分配，限制并发和最大输出；失败重试进入成本审计。

粗略价值测算使用试点观测：月任务数 × 每任务净节省工时 × 客户认定的人力成本，减去订阅/部署/模型/复核成本。净节省为负或错误风险高的场景不强推自动化，调整为辅助审阅。没有试点数据前不承诺 ROI、收入或确定的回本时间。

## 12. 完整交付包

交付包目录建议：

```text
release/
  manifest.json                 # commit、镜像摘要、schema、引擎、协议、兼容范围
  images/ 或 registry-manifest   # 在线/离线制品说明
  deploy/                       # Compose/企业平台配置，全部无秘密
  migrations/                   # dry-run、校验、备份、回滚限制
  licenses/                     # SBOM、NOTICE、授权清单
  manuals/                      # 用户、Admin、运维、事故、升级
  evidence/                     # 自动测试、真实模型/数据源、UAT、性能、恢复
  limitations.md                # 只读/不支持/已知问题与安全边界
  handover.md                   # 责任人、告警渠道、资产、有效期和签收
```

生产 Key 不打包进制品；通过客户秘密管理系统分发。移交时验证客户能独立部署、登录、配置、执行完整业务、接收告警并从备份恢复。只有这些通过，才可把项目状态从“开发完成”改为“企业交付完成”。
