# T03a: real Argon2id + PostgreSQL + one-time admin CLI checkpoint

> 2026-11-16 · Branch `feat/dyoffice-web` · Status: **T03a core implementation integrated; production login is still disabled.**

## Delivered code

- `apps/web/server/auth/passwords.mjs` uses the real `argon2` native package, Argon2id with memory 19,456 KiB, timeCost 2, parallelism 1, and 32-byte derived output. Every stored hash uses randomized salt generated by the library. The wrapper bounds concurrent password operations, validates PHC parameters and fails closed on malformed stored hashes; it never falls back to SHA-256/scrypt.
- `apps/web/server/db/postgres.mjs` provides a connection-limited `pg` pool for privileged schema/bootstrap operations, deliberately separate from future least-privilege application connections.
- `apps/web/tools/bootstrap-admin.mjs` is a trusted CLI only, not an HTTP endpoint: explicit deployment ID + login name, hidden TTY confirmation (or explicitly opted-in password-stdin), migrations first, then transactional initial admin/role/workspace setup. No password in argv, no default account or password, no detailed DB errors dumped to terminal.
- `apps/web/package.json` pins `argon2@0.45.2` and `pg@8.23.1`. Both `apps/web/package-lock.json` and the root `package-lock.json` were generated by a verified GitHub Actions job, and the dependency compatibility lock inventory was regenerated. The temporary workflow that generated these files was removed after successful completion.
- `apps/web/test/integration/local-identity.test.mjs` verifies real password hashing/verification, random salt, PostgreSQL migrations/replay, duplicate initialization and two competing first-admin bootstraps. `bootstrap-cli.test.mjs` covers CLI arguments, bounded non-echoed secret stdin, and refusal to accept password flags.
- `.github/workflows/dyoffice-identity-schema.yml` now installs actual Web dependencies, runs PostgreSQL 16 integration tests, invokes the real CLI against PostgreSQL and verifies SQL constraints. The SQL fixture uses an independent temporary schema and rolls back so it does not clash with the migration runner.

The identity CI exercises a disposable PostgreSQL database and test-only credentials. It is not a production security assessment. Previous failed CI runs were due to the SQL constraint fixture re-creating tables from an already applied migration. They were fixed by isolating the fixture in a temporary schema, not by weakening the database constraints.

## Still release-blocking

1. **T03b:** login/logout/me endpoints, server-owned sessions, secure HttpOnly cookies, CSRF and Origin checks, user-enumeration prevention, IP/account hash rate limits and session invalidation.
2. **T03c:** Admin user creation, activation and password reset tokens, roles and disable actions with reauthentication and audit.
3. **T04:** least-privilege database app role, row-level security, cross-user access denial for files/sources/conversations/jobs, and transaction pool-contamination tests.
4. **T03a hardening:** production-grade offline breached/common password screening beyond the small current prefilter, password memory/concurrency benchmarking on target machines, verified backup and emergency admin recovery procedures.
5. **Release:** current Web app still uses development Bearer tokens and intentionally refuses `NODE_ENV=production`. The new local password store is **not yet wired to user-facing routes**. No claim of production login or native Office editing.

Implementation direction remains strictly local username/password without OIDC/SSO. See [local-account-auth.md](../local-account-auth.md) and [acceptance-matrix.md](../acceptance-matrix.md).

The two intermediate failed identity runs were diagnosed: the first introduced test line was truncated during a file update, and a later patch accidentally retained duplicated invalid tail text. The test file has been reduced to a single valid test body; the repaired run passed. These were test-source syntax failures, not failures in Argon2id hashing or PostgreSQL transaction behavior.
